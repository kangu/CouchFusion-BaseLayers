# Dev module preload (prototype)

Date: 2026-10-31. Status: prototype, measured on hydra1 (radustanciu), not committed.

## Problem

In `nuxt dev`, Vite serves every source file as its own ES module. The browser only discovers a module's imports after fetching it, so a page loads one import level per round trip. The builder (`/builder/`) is 14 levels deep (`entry` → plugins → routes → `pages/builder/[[...target]].vue` → InlineLiveEditor → ContentAdminWorkbench → Workbench → … → minimark). Over the tailnet (about 60 ms RTT, lossy Wi-Fi) a warm builder load spent about 3.3 s just walking that chain, although almost everything was already cached.

## What it does

`utils/dev-module-preload.ts` is a dev-only Nuxt module registered by the layer:

1. It inlines `runtime/dev-preload/client.js` at the top of every page's `<head>`.
2. The script asks `GET /_nuxt/__cf_dev_preload?key=<first path segment>` (plus `~inline` for `?inline-preview`) for the module URLs that kind of page loaded last time, and adds a `<link rel="modulepreload">` for each. The browser then fetches the whole graph in parallel.
3. After `load`, once no new module has arrived for 3 s, the script reports what this load actually fetched (`POST` same URL), and again whenever more arrive, up to 60 s. A preloaded URL whose path was imported under another query (new `?v=` after dependency re-optimization, `?t=` after HMR) counts as stale and is dropped.
4. A client-side Vite plugin (`configureServer`) serves the endpoint and keeps the lists in memory and in `<buildDir>/cache/cf-dev-preload.json` (at most 50 keys, 5000 URLs each; only `/_nuxt/` paths; POST must be same-origin).

## Debugging is unchanged

Same module URLs, same transforms, same source maps, same HMR and stack traces. Only the moment the browser starts each fetch changes. A preloaded module is not executed until something imports it; a stale preload is a wasted request, nothing more.

## Switches

- Off in production builds (`nuxt.options.dev` only).
- Off for an app: `COUCHFUSION_DEV_PRELOAD=0` or `runtimeConfig.content.devPreload = false`.
- Off for one load: `?cf-preload=off`. Skip and record a fresh list: `?cf-preload=reset`.

## Caveats

- The first load of a page after the list is cleared (new build dir) records only; the second load benefits.
- Adding the module changes the Vite config hash, so the first dev start re-optimizes all dependencies once (new `?v=` hashes).
- Modules that are no longer imported stay in the list until a `?cf-preload=reset` load (harmless).
- After every dev restart Vite still discovers `minimark`, `minimark/hast` and `@noble/hashes/*` late and reloads the page once. `optimizeDeps.include` would fix that, but only per app (radustanciu does not list `minimark` itself), so it is not part of this prototype.

## Results

### Local dev with 60 ms added latency (Canary, CDP network emulation)

Medians of 4 warm and 2 cold loads each, "modules done" = last script of the page finished:

| Page | Warm, off | Warm, on | Cold, off | Cold, on |
|---|---|---|---|---|
| `/` (homepage, 271 scripts) | 2.19 s | 1.89 s | 4.10 s | 3.77 s |
| `/login` (228 scripts) | 1.53 s | 1.36 s | 3.41 s | 3.22 s |

Only 12–14% faster. Local `nuxt dev` speaks HTTP/1.1, so Chrome opens at most 6 connections to it, and the preloaded requests queue behind each other. The VPS slot is reached over HTTPS/HTTP/2 through `tailscale serve`, with no such limit, so it has to be measured there.

### hydra1 over the tailnet (Canary, HTTP/2 through `tailscale serve`)

Builder (`/builder/`, 744 requests, 365 scripts), 6 warm loads each, alternating `?cf-preload=off` and on. The link swung between clean periods and bursts of loss/delay (ping 40–147 ms, one burst with 25% loss), so the runs fall into two groups:

| Warm builder load | Preload off | Preload on |
|---|---|---|
| Modules done, clean periods | 2.4–2.7 s | **0.94–0.95 s** |
| Settled, clean periods | 4.6 s | 4.0–4.2 s |
| Modules done, during bursts | 14–26 s | 3–9 s |

- On a clean link, module loading drops by about 60% (2.5 s → 0.95 s). The page as a whole settles about 0.5 s sooner. The rest of the load (about 3 s) is the API calls and the inline preview frame, which only start after the app has started.
- While the link is bad, preload helps more: one long burst of parallel requests suffers less than 14 waves of them.
- Bytes are unchanged: the login page transferred ~98 kB with preload on and off (everything else from disk cache), so no file is downloaded twice.
- Cold loads could not be compared: the builder session (CouchDB, about 10 minutes) expired mid-run, so those loads ended on `/login`.
- Open question: with preload on, CDP reports far fewer 304s on the builder (15 vs 113). Transferred bytes were not measured on the builder because of the expired session.
- A page that redirects (builder → `/login` when signed out) records its modules under the key of the page it started on, so the `login` list gained ~50 extra entries. Harmless (they come from disk cache) and cleared with `?cf-preload=reset`.

## Next

- The remaining ~3 s of a warm builder load is the API calls and the inline preview after startup. Lazy-loading builder panels that are hidden at start, and starting the preview earlier, are the next levers.
- `optimizeDeps.include` per app for `minimark`, `minimark/hast` (and `@noble/hashes/*` where used) to avoid the reload after every dev restart.
