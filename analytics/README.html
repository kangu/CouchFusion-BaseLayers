Analytics Layer Guide

Privacy-friendly, self-hosted web analytics for CouchFusion apps. Each app tracks one website: its own. It collects pageviews and events, stores them in CouchDB, and gives you a dashboard with realtime, reports, sessions, sharing and an API.

No cookiesVisitors are counted with a hash that resets every day.
No third partyEverything runs in your app and your CouchDB.
No stored IPsOnly coarse details like browser and country are kept.

What you get

FeatureWhat it does
DashboardVisitors, visits, pageviews, bounce rate, visit duration, events and revenue, with a time chart and comparison to the previous period.
BreakdownsPages, entry and exit pages, titles, hosts, referrers, channels, UTM parameters, countries, regions, cities, languages, browsers, OS, devices, screens, events, event properties, tags. Click a row to filter by it.
World mapA dotted map on the overview with visiting countries highlighted. Hover for numbers, click a continent to zoom in for a more detailed view. When zoomed, click a highlighted country to filter by it, or click elsewhere to zoom out.
RealtimeActivity in the last 30 minutes, refreshed every 10 seconds.
ReportsGoals, funnels, journeys, retention, UTM, attribution, revenue, multi-dimension breakdowns.
SessionsEvery visit with its full event timeline.
Sharing and accessA public read-only link, viewer roles, API keys with a REST API.
ExtrasTracking pixels for emails, tracked short links, CSV export, import from Umami and Fathom Lite.

How it works

  1. Collect. The browser sends each pageview and event to POST /api/stats.
  2. Filter and enrich. The server drops bots, Do-Not-Track visitors, ignored IPs and excluded paths. It then works out browser, OS, device, country (from CDN headers), referrer, channel and UTM parameters.
  3. Anonymise. The visitor becomes a hash of a daily random salt, the site, the IP and the user agent. The IP and user agent are never stored.
  4. Store. Hits are written in batches to a raw-event database, one per month.
  5. Aggregate. Every 60 seconds a background job turns raw hits into one rollup document per website per day.
  6. Query. Unfiltered dashboard views read rollups. Filters, reports, sessions and realtime read raw hits, limited to 31 days by default.

Setup

  1. Add the layers 
    // apps/<app>/nuxt.config.ts
export default defineNuxtConfig({
  extends: [
    "../../layers/database",
    "../../layers/auth",
    "../../layers/analytics",
    "../../layers/admin_workspace", // admin layout + sidebar
  ],
  runtimeConfig: {
    public: {
      appSlug: "my-app", // selects the CouchDB section cf_env_my-app
      analytics: {
        admin: { enabled: true }, // adds /admin/analytics/** and the sidebar section
      },
    },
  },
});
  2. Install the dashboard packages in the app 
    bun add apexcharts @iconify/vue
  3. Let Tailwind see the admin layout (Tailwind v4 apps) 
    /* app/assets/css/main.css */
@source "../../../../../layers/admin_workspace/**/*.{vue,ts}";
@source "../../../../../layers/auth/app/**/*.{vue,ts}";
  4. Turn the engine on in CouchDB Add these keys to the _config section cf_env_<appSlug>: 
    analytics_mode = self_hosted
    That's all the engine needs. On first start it creates the app's website record by itself, named after the app slug.
  5. Review the website settings Log in as a user with the admin role and open /admin/analytics/settings. Set the display name and timezone, list the site's domains (while the list is empty, any hostname is accepted), and keep /admin* and /login in Excluded paths.
  6. Check it Open a public page of the site, then look at Realtime. The hit appears immediately. Overview totals follow within about a minute.
If the app has no /admin page yet, add one that uses the admin-workspace layout. apps/kangu/app/pages/admin/index.vue is a working example.

Tracking

Automatic

Once the layer is extended, every route change in the Nuxt app is tracked as a pageview. Nothing else is needed.

Custom events

<script setup lang="ts">
const analytics = useAnalytics();
const onSignup = () => analytics.trackEvent("signup", { plan: "pro" });
</script>

<template>
  <button v-analytics="'cta-click'">Start</button>
  <button v-analytics="{ event: 'cta-click', data: { location: 'hero' } }">Try it</button>
  <a v-analytics:mouseover="'pricing-hover'" href="/pricing">Pricing</a>
</template>

Event data must be flat: up to 20 properties, values up to 200 characters.

Revenue

analytics.trackEvent("purchase", { revenue: 49, currency: "EUR", plan: "pro" });

Identifying logged-in users

analytics.identify(user.id, { plan: "pro" });

Later hits carry that id. Retention and multi-day attribution need it, because anonymous visitors get a new hash every day.

Pages outside the Nuxt app

If part of the website is served elsewhere (a static landing page, a docs site on a subdomain), list that domain under Settings → Domains and add this to those pages:

<script defer src="https://your-app.example/a.js"></script>

No website id is needed: every hit goes to the app's one website.

Supported attributes: data-auto-track="false", data-domains, data-tag, data-exclude-search, data-exclude-hash, data-do-not-track, data-before-send, data-host-url.

In page scripts use umami.track("event", { key: "value" }) and umami.identify("user-id"); the same functions exist as cfa.track and cfa.identify. In HTML use <a data-umami-event="cta" data-umami-event-plan="pro">.

Roles. Users with the CouchDB role admin see and manage everything. For read-only access, give a user the analytics_viewer role and add that role under Settings → Viewer roles.

Filters. Click a row in any table to filter by it. Filters combine, live in the URL, and can be saved as segments.

Theme. The dashboard follows the admin workspace and is light by default. It turns dark only when a parent element has a dark class or data-theme="dark".

Configuration reference

All keys live in CouchDB _config, section cf_env_<appSlug>, as flat strings. Most can be edited under Settings → Engine. Changes apply within about a minute, with no restart.

Website settings (name, domains, timezone, excluded paths, goals, viewer roles, share link) are edited on the Settings page.

Country detection

The engine reads the visitor's country from a header the CDN adds to every request. Nothing is looked up, no IP database is installed, and the IP is not stored.

  • Cloudflare sends CF-IPCountry when the site is proxied (orange cloud) and Network → IP Geolocation is on, which is the default. For region and city, enable the managed transform Add visitor location headers.
  • A reverse proxy between Cloudflare and the app (Caddy, nginx) is fine as long as it forwards request headers. Caddy's reverse_proxy does this by default; don't strip CF-IPCountry or CF-Connecting-IP with header_up -....
  • CloudFront (CloudFront-Viewer-Country) and Vercel (X-Vercel-IP-Country) headers are read too.
  • Check it: Settings → Engine shows how many hits since the last server start carried a country.
  • Local development has no CDN in front, so no countries are recorded there.
The headers are trusted as sent. If the app can be reached directly, bypassing Cloudflare, a client could fake its country. Restrict the origin to Cloudflare if that matters.

Privacy model

  • No cookies and no local storage by default.
  • Visitor id = sha256(daily salt | site | IP | user agent), shortened to 64 bits. The salt is random, changes every day in the site's timezone, and is deleted after two days. After that the hash can't be linked back to anyone.
  • Never stored: IP address, full user agent, and query strings other than UTM parameters (unless you enable "Keep query strings").
  • Stored per hit: path, title, host, referrer domain and path, channel, UTM values, browser, OS, device type, screen size, language, country (plus region and city when the CDN provides them), event name and properties.
  • Unique visitors are per day. A range total is the sum of daily uniques, like Fathom and Plausible. Someone who visits on three days counts three times.
  • Bots are dropped on the server: crawlers, link previewers, headless browsers and scripts.

Sharing, API keys, pixels, links, import

Share link

Settings → Public share link. Anyone with the link gets a read-only dashboard. Rotate or revoke it at any time.

API keys and REST API

Create keys on the API keys page. A key is shown once. Use it as a bearer token:

curl -H "Authorization: Bearer cfa_…" \
  "https://your-app.example/api/analytics/v1/stats?range=30d&compare=1"
EndpointReturns
GET /api/analytics/v1/siteThe website's name, domains and timezone
GET /api/analytics/v1/statsTotals and time series
GET /api/analytics/v1/metrics/:dimensionTop rows for a dimension, such as page or country
GET /api/analytics/v1/realtimeLast 30 minutes
GET /api/analytics/v1/sessionsVisits, newest first
POST /api/analytics/v1/reports/:typegoals, funnel, journey, retention, utm, attribution, revenue, breakdown

Query parameters: range (today, yesterday, 24h, 7d, 30d, 90d, 12m, this_month, last_month, this_year) or from/to as YYYY-MM-DD; filters as a JSON array of { dim, op, value }; limit; offset.

Tracking pixels and links

Both are on the Pixels, links & import page. A pixel is an invisible image for emails or external pages; each load is a pixel-view event. A tracked link, /l/<slug>, records a link-click event and redirects.

Export and import

  • CSV export: the CSV link on each dashboard table.
  • Umami import: upload the website_event CSV and optionally the session CSV. Rows become raw hits, so filters and reports include them.
  • Fathom Lite import: upload hourly site_stats, page_stats and referrer_stats CSVs. They appear in dashboards but not in filtered views or reports.

Operations

DatabaseContents
analytics_<slug>The website record, day rollups, salts, segments, saved reports, API keys, pixels, links, aggregator lease
analytics_<slug>_raw_<yyyy>_<mm>Raw hits for that month

Both are readable by CouchDB admins only.

  • Aggregator. Runs inside the app every 60 seconds. With several instances, a lease in CouchDB makes sure only one aggregates. An instance that is killed hard can hold the lease for up to three minutes.
  • Retention. Whole monthly raw databases are dropped once they are older than analytics_raw_retention_months.
  • Rebuild. Settings → Data → Rebuild recomputes rollups for a date range from raw hits.
  • Reset. Settings → Data deletes all collected data after you type the website id.
  • Capacity. Today's hits are kept in memory for aggregation. Plan for roughly 100–200k hits per day per app.
  • Backups. Back up analytics_<slug>. Raw month databases replicate like any CouchDB database.

Troubleshooting

SymptomLikely cause
My own visits don't showYou only visited /admin* or /login, which are excluded. Open a public page.
Hits appear in Realtime but not in OverviewRollups refresh every 60 seconds.
Nothing is recorded at allanalytics_mode isn't self_hosted (the server log prints the mode at startup), or "Collecting" is switched off in Settings.
A browser never shows upIt sends Do-Not-Track or Global Privacy Control (Brave does by default), or its IP is in analytics_ignore_ips. Settings → Engine lists how many hits were dropped and why since the server started.
Hits from another domain are droppedThe domain isn't listed under Settings → Domains.
No countriesThe app isn't behind a CDN that sends country headers, or a proxy in between strips them. See Country detection.
Automated tests aren't countedHeadless browsers are treated as bots.
"Filtered queries are limited to 31 days"Raise analytics_max_scan_days, or remove the filter.
/admin shows "Page not found"The app has no /admin page. Add one with the admin-workspace layout.
Admin sidebar is unstyledTailwind isn't scanning layers/admin_workspace. See setup step 3.

Legacy: Umami Cloud forwarding legacy

The layer started as a proxy to Umami Cloud. That still works and is the default while analytics_mode is unset, so existing apps keep behaving as before:

  • umami_cloud: forward only, nothing stored locally.
  • dual: store locally and forward. Useful for comparing numbers during a migration.

New work should use self_hosted. Setup notes for forwarding are in docs/umami-cloud-forwarding.md.
