# Analytics layer: performance and resilience audit (2026-10-28)

Read-only multi-agent review of the working tree (after the Umami removal). 8 area reviewers produced 66 findings, 50 after dedup; each was checked by a correctness skeptic and an impact skeptic. 40 survived, 10 were refuted. Nothing was changed by this audit.

Spot-checked by hand: the `push(...docs)` crash (RangeError at 125k items, reproduced in Node), the unbounded raw reads, the per-tick today/yesterday recompute, the silent `_config` fallback, the missing body limit, and the stale title / failed-navigation pageviews.

## Confirmed findings

1. **[high · resilience · effort M]** `server/engine/storage.ts:41` — Raw scans put every event of up to maxScanDays into memory, with no event-count cap and no concurrency limit (reachable from the public share token and v1)
   - Scenario: A site with 50k hits/day and the default 31 days gives about 1.5M raw docs. A synthetic 300k-event array measured about 115 MB of heap, and JSON-parsed docs with `_rev` and unshared strings are larger, so one scan can reach roughly 0.6–1 GB. The dashboard fires about 8 of these at once (finding 1), and a share-link holder can keep re-requesting filtered views. The Nitro process that also serves the public website and `/api/stats` can hit OOM or stall GC. Queued hits that are not yet bulk-written are lost on crash.
   - Fix: (a) Stream instead of materialising. Add a `forEachRawPage(config, siteId, from, to, cb)` built on `scanRange`. buildVisits needs per-visitor grouping, but storing only the compact fields used (ts, t, v, p, n, d…) and dropping `_rev`/`_id`/`site` already cuts memory a lot. (b) Enforce a hard cap (e.g. `analytics_max_scan_events`, default 500k) that throws `QueryError(413, 'Range too large for a filtered query')`. (c) Put a global semaphore around raw scans (2–3 concurrent, the rest queue) and dedupe them (finding 1).
   - Verifier caveats: First, and quickest: replace `events.push(...docs)` at storage.ts:56 with a loop or `for await` page append, or have readRawEvents iterate `scanRange` directly. Otherwise any event cap above about 120k per shard just turns into a RangeError, and the aggregator paths (aggregator.ts:89, 109) stay broken for high-volume days. Check the same pattern anywhere else a large array is spread. Apply the event cap inside the page loop, before memory is used, and not after collectRange returns. Exclude the aggregator's own reads from the cap, or give them a much higher one, because day finalisation must stay authoritative. If a semaphore is added, give the aggregator a separate slot or exempt it, so dashboard load cannot starve the lease-held tick. Projecting docs down to compact fields means checking every field that computeRollups, buildVisits and reports read (including `_id`, which the tail cache uses as its Map key, aggregator.ts:110). | 1) First, and on its own: replace `events.push(...docs)` in storage.ts:57 (and any other spread of an unbounded array) with a for-of push loop, or stream pages straight into the consumer. This is the fix that stops the crashes, and it changes no data format. 2) Check the event cap while streaming, by counting pages and aborting early. Checking after materialising does not save the memory. Apply it only on the dashboard, report and share paths, never on the aggregator's readRawEvents calls (computeDayFromRaw, loadToday), or high-volume sites would never get rollups. 2. **[medium · performance · effort M]** `server/engine/aggregator.ts:105` — Every 60 s tick recomputes the whole of today from an unbounded in-memory tail, and GETs plus diffs the full rollup doc even when nothing changed
   - Scenario: Site with 300k events/day. By evening the leader holds roughly 300k+ full docs in the heap (hundreds of MB, plus the per-visitor arrays and filter copies made each tick) and spends seconds of synchronous CPU per minute in buildVisits/computeRollups, which blocks the event loop that also serves POST /api/stats and dashboard requests. Quiet sites still pay for a full recompute, a full rollup GET and two stringify calls every minute overnight. An instance that loses the lease keeps its tail in memory until the process exits.
   - Fix: (1) Track whether the tail scan inserted any new _id. If none did, skip computeRollups and storeRollup. (2) Keep the last written rollup's stable hash and _rev in memory per (site, day), and only GET the doc on a 409 or a rev mismatch. (3) Strip fields the rollup doesn't need (e.g. _rev) when caching. (4) Drop `tails` for the site when acquireLease returns false. For very large sites, consider capping tail size and falling back to periodic raw recompute.
   - Verifier caveats: (1) Do not use "no new ids this tick" as the skip condition. Keep a per-tail `dirty` flag (or the last successfully stored id count or hash), and clear it only after `storeRollup` succeeds. Otherwise a write that throws (a CouchDB blip) is never retried until the next new event arrives. This matters most on quiet sites and for the last events of the day. Always store at least once per tail creation, i.e. after a restart or a day change, because the stored doc may be stale or missing. (2) If you cache the rollup's hash and `_rev` in memory, keep writing through `upsertDoc` and treat the cache only as a hint for skipping the write. `rebuildRange` can run on a different, non-leader instance from an admin request and write the same doc. It clears only that instance's `tails`, not the leader's, so the leader's cached `_rev` can go stale. (3) Stripping fields: `computeRollups` reads almost every field (dims, `utm`, `d`, `uid`/`pid`, etc.), so only `_rev` and other fields the rollup never reads are safe to drop. The memory saved is modest. (4) Clearing `tails` when `acquireLease` returns false is safe. When the instance regains the lease, it does a full reseed, which costs one larger read. (5) A tail cap with a raw-recompute fallback would bring back the full raw scan that this cache exists to avoid. If you add one, size it carefully and, ideally, make the computation incremental, e.g. recompute only the visitors touched by new events. A plain cap is not enough on its own. | - **Fix (1), skip when no new _id, is safe but low value.** computeRollups does not depend on `now`, so skipping a recompute when nothing new arrived is correct. But a busy site has new events almost every minute, so this barely touches the 3 s/tick cost. Detect "new" by checking `!tail.events.has(id)` while merging the overlap scan. - **Fixes that actually remove the cost:**   - (a) Memoize localParts/localHour/localDay per timezone by time bucket, for example floor(ts/60000) in a small Map, or a per-hour offset cache that handles 30/45-minute offset zones. Measured at about a third of compute time. This is pure and changes no output.   - (b) Recompute incrementally. Keep the previous visit set and recompute only the visitors touched by new events. This is harder because of the visitor Sets and the 500-entry dim cap, so it needs care.   - (c) Cap the tail size, or yield between sites/chunks so POST /api/stats is not starved. - **Drop fix (2), the cached hash/_rev that skips the GET.** The GET of a ~80 KB doc once a minute is trivial. The cache would go stale whenever another instance runs rebuildRange or resetSiteData through admin routes. Both write or delete agg docs, but they only clear `tails` on their own process (aggregator.ts:206, 229). With a cached hash the leader would then skip needed writes. - **Existing multi-instance bug worth fixing alongside.** resetSiteData on a non-leader deletes raw events and rollups, but the leader's in-memory tail still holds the deleted events. On its next tick the leader rewrites today's rollup from those deleted events. Fix (4), dropping tails when acquireLease returns false, does not cover this, because the leader keeps the lease. Invalidation needs a shared signal, for example a reset or rebuild generation counter on the state:<site> doc that loadToday checks. - **Fix (3), stripping _rev, is safe:** rollup.ts never reads it, and it saves only ~5-10% of tail memory. Keep _id, because buildVisits uses it as the sort tie-breaker. - **Fix (4)** is safe. When the lease is lost, clear all of `tails` (it is keyed by prefix:site, and the lease is global), not just one site's entry.
3. **[medium · performance · effort S]** `server/engine/aggregator.ts:143` — For 3 hours after every local midnight, yesterday is fully re-scanned from raw on every tick (~180 full-day recomputes per night)
   - Scenario: Site with 200k events/day: between 00:00 and ~03:02 local time the leader re-reads about 250k raw docs (around 125 paged _all_docs include_docs requests) every minute, about 45M doc reads per night, and rebuilds the full rollup each time. Keep a per-site in-memory `lastYesterdayCompute` timestamp and recompute at most every 15–30 min while withinMargin. Once the window ends, the existing logic already finalizes the day on the next tick: yesterday is still pending because finalizedThrough < yesterday, and `!withinMargin` is now true. ## 2. Completeness critic (unverified-by-panel)

- **G1. `storage.ts:56` `events.push(...docs)` throws RangeError at about 125k docs per shard.** I confirmed with Node: 100k works, 130k throws.
  - `readRawEvents` is used by `computeDayFromRaw` (`aggregator.ts:89`), `loadToday` (`:109`), and every filtered, report, session and realtime query.
  - Scenario 1: a site with about 5k hits/day opens a filtered 31-day view. That is about 155k docs in one month shard, so the request returns 500.
  - Scenario 2: a site with about 100k hits/day. The 30 h window for today or yesterday crosses the limit, so today's rollup stops updating and yesterday never finalizes.
  - The panel only mentions this inside caveats. It should be a standalone P0 item (T0).
- **G2. Today's step failing blocks finalization (`aggregator.ts:133-135`, before `:147-156`).** There is a single try/catch per site (`:185-189`). If `loadToday`, `computeRollups` or today's `storeRollup` throws (RangeError, 413, timeout), yesterday and the backfill never run and `finalizedThrough` stalls. Retention (`:161-175`) keeps dropping shards whether or not the days in them were finalized, so a long stall can lose days permanently. Fix: give today and backfill separate try blocks, and don't drop shards newer than `finalizedThrough`.
- **G3. Rollup revision churn and a double GET.**
  - Every tick that changes content rewrites today's `agg:` doc (`aggregator.ts:81`). On a busy site that is up to about 1440 revisions a day of a 100–250 KB doc, plus `lock:aggregator` every minute (`:34`).
  - The layer sets no `_revs_limit` and runs no compaction anywhere (grep found nothing). It relies on CouchDB 3's smoosh auto-compaction. On 2.x, or with auto-compaction turned off, the main DB grows by hundreds of MB a day.
  - Each write also does two full-doc GETs: `storeRollup`'s at `:71`, then `upsertDoc`'s at `couch.ts:100`.
  - Fix: pass `existing._rev` straight to `putDoc`, and fall back to `upsertDoc` only on 409. Optionally write today's doc every N minutes unless the day is closing, and document the compaction requirement.
- **G4. The tail-overlap window is the hidden coupling for every queue change** (`aggregator.ts:19`, `:113-115`). The 2-minute overlap is safe only while flushes land within about 2 minutes. T3, and the long bulk timeouts in T2, both break that assumption unless `lastTs` is clamped to the oldest pending ts. It is already listed as a required part of T3. Treat it as a blocker, not a caveat.
